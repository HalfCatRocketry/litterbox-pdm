# Changelog

## 0.4.1

- Fixed: buttons only worked when clicked near their middle (since the move to CustomTkinter 6). The whole button works again, and it still acts when the mouse button is released over it.
- The open org's full name is shown in the middle of the menu bar (hidden on a window too narrow for it).
- When the details pane is hidden, a **«** button at the right end of the toolbar brings it back. The pane is always open when Litterbox starts; hiding it lasts until you close Litterbox.
- **Importing files imported before.** When a scan finds files the vault remembers importing, the Import window now warns, lists them with the part numbers they were imported as, and lets you go on (they are imported again as new parts, ticked in the table, so you can still untick any) or cancel. Before, they were quietly left out, and if that was everything the import stopped with "nothing left to import". The command line still leaves them out unless the manifest says `include: true`.
- The sidebar's My Tasks and ECOs are under a new **PROCESS** heading, as the parts views are under PARTS.
- **A tidier Team screen.** Who am I? and Signing... sit beside your name; the people buttons (Add Person, Edit, Switch On/Off, and **More** with Transfer Ownership...) sit above the list; Roles, Workflows, Projects and Vault Settings are in an **Organization** panel on the right. Buttons you can't use are greyed out with a tooltip saying why, instead of being left off. Unsaved changes show at the top right with **Save** and a new **Discard**. Double-click a person to edit them; the line under the list shows the highlighted person's roles, host names and signing keys (those columns left the table).

## 0.4.0

- **Create new org** (was Create new vault): the boxes are in a clearer order (digits before the first number), the first number follows the digits (100001 for 6), and an example part number (123456-001) is shown beside the digits.
- **The org name can be changed** by the Owner, in Team > Vault Settings... The org code and part number scheme still can't.

- **A new main window.** Everything is still there, laid out the way other PDM programs do it:
  - A **menu bar** (File, Vault, View, Help; Alt+F, Alt+A, Alt+V, Alt+H) with the Litterbox logo on the right. Adding an org and Create new org (was Create new vault) moved from the org box to the File menu; the org box in the header now lists only your orgs. Check for updates and the version are under Help.
  - A **sidebar** on the left: the parts list's views (All, Mine, Checked out, Released, Not downloaded, Void) with how many parts each has, then **My Tasks**, **ECOs** and **Team**, which are now screens in the main window instead of separate windows (Ctrl+1 to Ctrl+4). The Show void box became the Void view. On a narrow window the sidebar shows only its icons; View > Sidebar names switches the names on or off.
  - Above the list, the four everyday buttons (Check Out, Check In, Save Progress, Undo Checkout), then **Open**, **Lifecycle** and **Create** menus for everything else. A greyed-out button says why when you rest the mouse on it; a greyed-out menu entry says why in the status bar. **Right-click** a part for the same actions.
  - The list's first column has each part's **tick box and a status icon** (a different shape for each status, so colour is never the only clue; Help > Status icons explains them). Resting the mouse on an icon shows the full status. The Status column is gone by default; long names and descriptions are cut with "..." and shown in full on hover. **Columns** chooses which columns are shown (Status, Checked out by, Released rev, Imported from and COTS are there to add).
  - **Search** can look in one column (the box beside it), and takes wildcards: `*` for any characters and `?` for one, matching the whole value (`Te*rt` finds Test Part but not My Test Part). Plain text still finds it anywhere.
  - A **details pane** beside the list follows the part you click: its status, and Details, History, Uses and Where used tabs. The button at its top opens the same in a window of its own; double-clicking a part does too. View > Details pane hides or shows it.
  - The header says how many changes others have uploaded that you haven't got yet ("2 changes to get"); click it to Get Latest.
  - The status bar along the bottom replaces the banner, the status line and the log box: a green, yellow or red dot, what just happened, what SolidWorks has open (when watching), the jobs waiting, and the **Log**, which opens as a drawer.
  - **Text that fits the screen.** The list, its icons, the menus and the tooltips now follow Windows' display scaling like the rest of the window (they were drawn at 100% before, so they looked small on high-resolution screens), and **View > Text size** (90% to 130%, Ctrl+= and Ctrl+-) makes everything bigger or smaller. Your columns, Text size and details pane choice are remembered.
- **Projects.** An Admin or the Owner can add projects (Team > **Projects...**): a name and the digits its part numbers start with. With 6-digit part numbers, project Rover starting `12` owns 120000 to 129999. New Part has a **Project** drop-down (None by default): choosing a project shows its digits in front of a shorter part number box that takes only the rest, suggests the next free number in its block, and checks what you type as you go. With None, Litterbox never hands out or accepts a number inside a project's block, and neither do Import and batch creation. A part's record says its project (`project: Rover`), a new variant is in its part number's project, and **Project** is a column you can add to the parts list and search in. Projects can't overlap. A new project's block may already hold parts, which keep no project (the Projects window says how many). **Edit** changes a project's name or digits and **Delete** removes it: Litterbox first lists the parts that join it, leave it or are renamed (after a change, a part is in the project exactly when its number is in the block), then changes their records together with the settings in one upload, with a history entry on each. It refuses, naming them, if any of those parts is checked out. A deleted project's numbers are free again. A vault with projects needs Litterbox 0.4.0 or newer.
- **New Assembly.** Create (and Vault) > **New Assembly** works like New Part, but its variants start at 500: a new assembly is HCR-00042-500, and New Part's variants stay below that (001 to 499). The org chooses the number in Create new vault (500 by default; 50 with 2-digit variants), and an Admin can change it at any time in Vault Settings. Typing a variant from the other range is allowed, but the window says so as you type and asks before creating it. Import does the same: an imported assembly gets variant 500 (and, imported as one family, the variants from 500 up while parts take those below), and an automatic number never shares its part number with another part. `new-part part --assembly` and `init-vault --assembly-variant` do the same on the command line.
- **Break Checkout (Admin and Owner).** Lifecycle > **Break Checkout...** (also on the right-click menu) takes a part back from whoever has it checked out, when they can't check it in. It asks why, releases their locks, and the part's history says who broke it, whose it was and why. Their changes are not uploaded. When they next sync, Litterbox puts the part back as it is in the vault, saves their versions of any CAD files someone has since changed in `C:\Litterbox\<vault>-recovered\<time>\`, and tells them where. Before, a sync would have stopped, or hidden their work in a git stash.
- **Syncing** now fetches, then rebases (what `git pull --rebase --autostash` does, in two steps), so the check above costs nothing extra: it only reads the lock list when a file you changed without holding its lock has also changed in the vault.
- **Create new vault clones the repository for you.** Paste the empty repository's URL (from your Git host's Clone button) with the org's settings; Litterbox clones it into `C:\Litterbox\<repository name>`, like Add org..., then sets up the vault as before. If a try stops part-way (Git doesn't know your email yet, say), the next try uses the copy it already made. Before anything happens it asks you to check the org code, org name, part-number format and first part number, because they can't be changed afterwards.
- **Org setup... is gone.** An org's code, name and numbering are fixed when its vault is created; changing them later could leave the vault's records and files not matching. If an org's vault folder goes missing, Add org... with the same URL copies it again.
- **STEP and PDF exports.** A STEP or PDF saved in the cad folder under the part's name (`HCR-00042-001_A.STEP` from the model, `HCR-00042-001_A.PDF` from the drawing) is part of that revision: it is checked out, checked in and undone with the part, and stays with its revision when the part is revised. Importing old CAD now brings along a `.STEP`, `.STP` or `.PDF` with the same name beside a model or drawing, copied as a plain file.
- **New vaults' `.gitattributes`.** Every rule now matches any capitals (`*.[sS][tT][eE][pP]`; Git and Git LFS only ignore case on Windows). STEP, PDF and other CAD formats (IGES, Parasolid, SAT, STL, 3MF, DXF, DWG, eDrawings) are Git LFS and lockable like SolidWorks files, anything else in `cad/` is too, and pictures, office documents, archives, video and SolidWorks templates go in Git LFS. Existing vaults keep their own `.gitattributes`.
- **Org name.** An org can have a full name as well as its code (`org_name: Hidden Creek Robotics` in `.litterbox/config.yaml`). Create new vault asks for it; `init-vault` takes `--org-name`. Older Litterbox ignores it.
- **New: engineering change orders (ECOs).** In the Workflows window each workflow has a **Require ECO** box (on for the standard Release T1, off for everything else). Starting a workflow with that box ticked shows an ECO form (Name, required, and Description) in the Workflow window, and Litterbox saves it as its own file, `ECO\ECO-0001.yaml`, numbered in order, in the same upload as the request. The ECO is closed when the request ends: Released when the last person signs, Complete is pressed or an Admin overrides; Rejected or Withdrawn otherwise, with who did it, the sign-offs and any comment. ECO files are read-only in every copy, like released parts, and only Litterbox changes them; a closed ECO is never changed again. If two people start ECO workflows at the same moment and pick the same number, the second one quietly takes the next number. The new **ECOs** screen (in the sidebar) lists every ECO, with a search box (number, name, description, part or person) and a status filter; View (or double-click) opens one, showing its description, parts, sign-offs and history. My Tasks, the confirmation question and the part's history show the ECO number too. A vault that uses Require ECO needs Litterbox 0.4.0 or newer.
- **Add Parts / Remove Parts in the Workflow window.** The parts a workflow starts on are now a list you can change before you submit: **Add Parts** opens a window to search the vault and pick more (only parts that can go through that workflow, aren't already waiting for sign-offs and aren't busy), and **Remove Parts** takes the selected ones out.
- **A part's Details tab.** A part's details (in the pane beside the list, or its own window) start on a new Details tab: a Revision drop-down (the newest revision first) shows that revision's state, who released it and when, the workflow and who signed it off, the ECO it was released with (with a **View ECO** button), its files and the parts it uses. Everything that was in the History window is on the History tab next to it.
- Fixed: if a Get Latest stopped part-way because someone else had changed the same file, your copy was left half-way through git's sync and later actions failed. Litterbox now puts your copy back as it was and reports the problem.
- **New: Litterbox can watch what SolidWorks has open** (switch it on with `solidworks_watch: true` in `C:\Litterbox\settings.yaml`). It then asks before Check In or Save Progress if any of those parts have unsaved changes in SolidWorks, asks before Get Latest if a file it may replace is open in SolidWorks, warns if you open or save a part while it is still being checked in, and after a download names only the updated files you actually have open. It only reads from SolidWorks and never starts it. Add `solidworks_popups: false` to have these notes go to the log instead of pop-ups. With `debug_mode: true`, the log lists every document SolidWorks opens, closes, changes and saves. Not yet tried with a real SolidWorks.
- **Download on demand.** Litterbox no longer has to download every CAD file in the vault. A vault added with Add org... gets the part records and history but leaves the CAD files on the server until you use them: Check Out downloads that part's files, Open and Open Drawing download what they open first (an assembly together with every part revision it uses), and Get Latest keeps the files you already have up to date without fetching the rest. The parts list shows "(not downloaded)" next to a part's status. Release, Unrelease, Void, Make COTS and workflow requests don't need the files, so they download nothing. Vault > Download All gets everything at once. To download everything all the time, add `download: all` to `C:\Litterbox\settings.yaml`; otherwise each vault is switched to download on demand the first time you open it (files you already have stay on your computer).
- Fixed: when Git LFS's own lock cache (`.git\lfs\lockcache.db`) got damaged, every check-out, check-in and the parts list's lock column failed with "lock cache initialization ... gob: bad data". Litterbox now moves the damaged file aside (keeping it as `lockcache.db.broken-<time>`), notes it in the log, and carries on; Git LFS starts a new one.
- The command line is now one command, run from the `app` folder: `python -m litterbox <command>`, with the commands `status` (and the part actions: latest, checkout, checkin, save, undo, release, makecots, reopen, void), `new-part`, `scan`, `import` and `init-vault`. Their options are the same as before; `python -m litterbox <command> --help` lists them. The old `python litterbox_engine.py ...`, `python create.py ...`, `python scan.py ...`, `python importer.py ...` and `python init_vault.py ...` no longer work. To start the program from source, run `python app/main.py`.

## 0.3.2

- Litterbox now works in the background. Actions no longer lock up the window: click an action, it joins a queue and runs in order, and you can keep browsing, ticking parts and queueing more. Opening the Import window and switching org still wait for the queue to finish.
- New status banner at the top of the window: green "Ready", yellow "Working" (what is running and how many jobs are waiting), red "Error". An error stays red until you dismiss it; Details... shows what went wrong and what to do about it. Real problems no longer interrupt you with a pop-up.
- Parts with a job queued or running show "checking in 3 parts..." in the Status column and can't have anything else done to them until it finishes. Check In and Save Progress ask you not to save those parts in SolidWorks until the banner says Ready, and Open warns if the part is still being uploaded.
- Closing Litterbox while it is still working asks first.
- Check In now notices a part that was saved in SolidWorks after you pressed it, or while Litterbox was reading it. That part is not uploaded; it stays checked out to you, and the message tells you to Check In again when you have finished saving. The other parts carry on. (Litterbox does this by comparing each file's size and modified time, which costs next to nothing; it does not change any file's read-only state. Save Progress only checks for a save during the upload itself, since you are meant to keep working after it.)
- Fixed: Add org... opened the Org setup form (code, start number, digits), which made no sense for a vault that already exists. It now asks for just the repository's URL (the https address from your Git host's Clone button), clones it into `C:\Litterbox\<repository name>` in the background, reads the org code and numbering from the vault itself, and opens it. If the URL is already added, or the clone turns out not to be a vault yet, it says so plainly (and points to Create new vault...). Org setup... is still where you edit an org.
- Create new vault... now suggests 6 digits in the part number (was 5). Vaults that don't say how many digits they use keep 5, so no existing vault changes.
- **Part numbers now loop.** Numbers count up from the vault's start number to the highest the digits allow (999999 for 6 digits), then start again at 1 and go up to just below the start number, so the start number is only the first point of a complete loop and every number gets used. Zero is never used. Voided parts keep their numbers.
- When every part number is taken, New Part, the suggested number and Import say so plainly ("this vault has no part numbers left") instead of complaining about the number of digits.
- **Import numbering counts from the lowest free part number.** It still proposes numbers about 100 ahead (plus a random extra, so two big imports started together are unlikely to collide), but the 100 is now counted from the lowest free part number, not from the highest one in use, so one number typed in far above the rest no longer pushes imports up with it. Past the highest number the digits allow, it loops round to 1. If someone takes a proposed number while you work, the numbers Litterbox chose are swapped for the next free ones when you finish, as before.
- Create new vault no longer warns about a high start number leaving little room, since the numbers loop round.

## 0.3.1

- **Actions on many parts are much faster.** Check Out, Check In, Save Progress, Undo Checkout, Release, Unrelease, Void and Make COTS, and every step of a workflow (asking, signing, finishing, withdrawing), now download once and upload once for the whole selection instead of once per part, and take and release locks several at a time. Each part still gets its own history entry. Changes to part records (workflow steps, Release, Unrelease, Void, Make COTS) go in one commit per batch, with a line for each part in its message; Check In and Save Progress still make one commit per part. If one part can't be done (somebody has it checked out, say) it is reported and the rest carry on; if the upload itself fails, nothing is left half done. Updating references on several assemblies, and Update references, work the same way.
- Parts you void are unselected automatically (they are hidden by default, so a leftover tick was invisible).
- Release, Unrelease, Void and Make COTS now work on several selected parts at once even in a vault with no workflow; before, they needed one part at a time.
- **Reopen is now called Unrelease** everywhere it is shown (the button, pop-ups, Team > Workflows and a part's history). Records and settings keep their old internal name, so nothing in an existing vault changes.
- **Buttons grey out** when they can't be used on what is selected: a button lights up only if every selected part suits it (for example Check Out is grey if any selected part is already checked out).
- Parts list: new **Deselect All** button.
- Import: "Import all as the same base number" box. Leave the number empty for the next free one, or type your own; if it is already in use the new variants start at the lowest free number. Litterbox refuses, and says so, if the parts won't fit in the variant numbers that are left.
- Import review: **Select All** and **Deselect All** buttons.
- Shift-click selects everything between the last click and this one in every list with boxes (Import, References).
- New vault setting commit_style: Check In and Save Progress on several parts make one commit per part (the default) or, if an Admin chooses it, one commit for the whole batch, which is faster (each commit takes about a second). Admins and the Owner change it in Team > Vault Settings...; it applies to everyone. The same dialog also edits release_rule (warn / block / off) and require_signatures, which were hand-edited in .litterbox/config.yaml before (turning signatures on asks first).
- Debug mode now logs where a batch's time went, e.g. `Timing: check in on 20 part(s) took 31.2s. git commit x20 = 19.8s; git push x1 = 6.1s; ...`.
- Very large batches (over 100 parts) now still make a single commit when one is asked for.

## 0.3.0

- Workflows are rebuilt. Pressing Release (or Reopen, Void, Make COTS) in a vault that has workflows for that action opens a Workflow window: pick a template (T1, T2... or your own), choose a person for each sign-off, add optional extra sign-offs, and submit. Several parts can go through one workflow together; the people sign once for the whole batch.
- Team > Workflows has a tab for each action. A template is a list of sign-offs; list a role twice for two sign-offs, and use "+ or" to let someone with any of several roles fill a sign-off (for example Manager or Chief). Each template says whether one person may fill more than one sign-off and whether the person who asks may sign. "Add standard workflows" adds Release T1, T2 and T3 and one workflow for each other action.
- The people who sign are named when the workflow starts; My Tasks shows each person what is waiting on them. The person who asked (or an Admin) can change who signs, withdraw the request, or finish it; an Admin can still override with a recorded reason.
- Release, Reopen and Void happen as soon as the last person signs. Make COTS waits for the button to be pressed again. Revise and Cancel Revision don't have workflows yet.
- Delete .litterbox/workflows.yaml before updating a vault that used 0.2.0 workflows, and set them up again in Team > Workflows. A vault with workflows asks everyone to update to 0.3.0.
- Check Out, Check In, Save Progress, Undo Checkout, Release, Reopen, Void and Make COTS act on the parts whose boxes are selected. Clicking a row highlights it in blue, which Open, Open Drawing, References and History use.
- Parts-list tick boxes now read "selected" throughout the program.

## 0.2.0

- **Release workflow.** An Admin can require sign-offs before a part is released (Team... > Workflows...). Pressing
  Release then asks the people holding the required roles; the part is released when everyone needed has signed.
- **My Tasks** lists the sign-offs waiting on you. Reject (with a reason), withdraw, and Admin override (with a
  recorded reason) are all there.
- Vaults that use a workflow ask everyone to update to 0.2.0 first.
- Team changes are saved together. The Person, Roles and Workflows windows have an OK button that keeps your change in a draft; the Team window's Save uploads everything at once. Cancel or Close with unsaved changes asks "Discard changes?" (Discard / Keep editing). Discarding in a sub-window drops only that window's changes.
- Tick boxes down the left of the part list pick several parts at once for Check Out, Check In, Save Progress and Undo Checkout.
- Saving when nothing changed now shows an information message instead of an error.
- Pop-ups opened from the Team window stay on top of it (for example Who am I?).

## 0.1.1

- **Create new vault...** in the org menu (and `init_vault.py` on the command line) turns an empty cloned
  repository into a vault: LFS and lock settings, ignore rules, the vault's settings, and the first Owner.
- Fixed buttons that only responded when clicked in the middle.
- A clearer message when the update check gets a 404 (usually a private repository).
