# Changelog

## 0.6.5

- **Report a problem lists exactly what goes in.** The window now shows each file the report will hold, about how big it is, and what it contains: report.txt (your comment, the versions, the problems and errors), Litterbox's log, your Litterbox settings and the vault's shared settings. Tick boxes leave out the log or the settings. It also says what is taken out (passwords and tokens) and what never goes in (CAD files, documents, part records, the team list). The report itself has a CONTENTS.txt with the same list. With Outlook, Litterbox offers to open the report before you send it.
- **Betas.** Help > **Get beta versions** offers betas (the next version before it is finished) as well as releases. A beta copy is offered the final version once it is out. Betas are best tried in a test vault or by the whole team at once, since a beta can make a vault need the version it leads to. Nobody is offered a beta without choosing to.
- **Signed notices.** Each update check also reads a notice signed by the maintainers' offline key. It can withdraw an update key that was stolen or lost (Litterbox stops trusting it straight away, even before updating), or say that Litterbox's releases have moved to another place, which Litterbox then follows. Either is kept in settings.yaml.
- **Licences.** The installed program now has a licenses folder beside Litterbox.exe with the licences of everything it is built with (Python, customtkinter, PyYAML, cryptography, pywin32 and the others).
- **Releases are built more safely.** The key that signs updates is now used only by the last step of a release, never by the steps that install packages, build the program or run the tests, and every package a release is built with is pinned to an exact, checked file.

## 0.6.4

- **My Tasks and All Workflows show new requests at a refresh**, without Get Latest: a request someone has just asked you to sign (or a change to one, or one withdrawn or finished) shows as soon as the list refreshes. A request your copy hasn't got yet says so under the list, and Review (or any of its buttons) gets the latest first, then carries on.
- **A workflow is recorded as done by whoever asked for it**, not whoever signed last: a release (the Details tab's Released, and the history), an unrelease, a void, a make-COTS, a document link taken off, and the dispositions that go with them. Who finished it is kept on the history event too (completed_by). Events from before 0.6.4 keep what they say.
- **Details line up.** In the Details tab, the document window, the Review window and the ECO window, each value now starts level with its label, also when it wraps onto more lines.
- **Windows fit the screen.** Every Litterbox window now opens no bigger than the desktop it is on (less the taskbar), at any display scaling, and is moved so its title bar and buttons are on screen. The Workflow and Review windows were too tall for a 1080p screen at 150%.
- **Git's name and email are asked for.** When a vault opens and git doesn't know your name or email address (git can't save changes without them), Litterbox asks for them, filled in from the team list, and sets them for that vault only. If git has a name other than yours on the team list, it offers the team list's (Keep as it is leaves it). Create new org asks before it starts, too.
- **Project settings.** Team > Vault Settings... has two more settings: **Who may add projects** (Admins and the Owner, the default, or anyone on the team) and **A project's starting digits** (at least 1 to one less than the part number's digits, or no minimum), so nobody sets aside too many part numbers. Anyone else is refused fewer digits; an Admin or the Owner is warned and may Proceed. Projects already made keep their digits. Whoever adds a project is now its Lead to start with (they can choose another). Turning either setting on makes the vault need Litterbox 0.6.4.

## 0.6.3

- **Cancelled revisions are kept in cad\cancelled-revs**, under the cad folder, instead of a cancelled-revs folder at the top of the vault. They are stored with Git LFS and read-only, like the rest of the cad folder: kept only for the history.
- **Purchasing columns.** View > Columns can show each part's **Supplier**, **Supplier part number**, **Unit cost** (with the team's currency) and **Lead time (days)** in the parts list. They are hidden to start with, and searchable; Unit cost and Lead time sort as numbers ($0.42 before $0.5). An assembly shows its own purchasing info, not a total of its parts' (the BOM tab adds those up).
- **Kits keep their BOM too.** A released non-CAD assembly (a kit) now gets its BOM saved with the release, like a CAD assembly: HCR-00042-500_A_BOM.csv in the cad folder, its only file.
- **A BOM that couldn't be saved with its release is flagged** ("BOM file needs saving"), and **Part > Save Released BOM** (or **Save BOM File** on the Details tab) saves it later, as things stand then. A BOM saved with its release is never saved again over it. Releases from before 0.6.3 are never flagged; Save Released BOM still saves a BOM for one that has none.
- **Export Files offers the saved BOM** (BOM saved at release, .csv) beside the model, drawing, STEP and PDF.
- **File rules version 4.** Vault > Update file rules... (an Admin or the Owner is asked once per session) adds the rule for the new folder and moves the vault's existing cancelled revisions there in the same upload, with their history. It makes everyone in the vault need Litterbox 0.6.3, so nobody keeps cancelling into the old place. It is offered again if an older Litterbox cancelled a revision into the old folder before the update. Until then, 0.6.3 already cancels into the new place, and a hidden project's cancelled revisions are left out of other people's copies in either place.

## 0.6.2

- **SolidWorks templates.** Litterbox now makes a part's files from the team's templates: part templates (.prtdot), assembly templates (.asmdot) and drawing templates (.drwdot).
  - **The org's and each project's.** The org has its own templates and each project can have more; one of each kind is the default, for the org and for each project. A part in a project gets its project's default if the project has templates of that kind, otherwise the org's; the others can be chosen instead.
  - **New Part and New Assembly** have a **Template** box, with the default chosen: Litterbox makes the model from it (HCR-00042-001_A.SLDPRT, in the cad folder) and opens it in SolidWorks. Choose None to save the model yourself, as before.
  - **Create > New Model...** makes the model of a part checked out to you that has none yet, and **Create > New Drawing...** its drawing, as an **empty sheet** of the template's size with its title block. Both ask which template, with the default chosen. The file goes up with the part's next Check In.
  - **Team > Templates...**: everyone can look; Admins and the Owner add, remove and choose the default of the org's templates, and a project's Lead (and Admins and the Owner) the project's. Templates are kept in the vault's new **templates** folder: the org's at its top, each project's in a folder of the project's name (templates\Rover), with templates/templates.yaml saying which is which. The org and each project may use the same file names. Each change is uploaded at once. An upload with template changes the person may not make is refused. A renamed project keeps its templates. An older Litterbox leaves the folder alone, so the vault doesn't need 0.6.2.
  - The user guide has a Templates section, with what to watch: keep the sheet format inside the drawing template (SolidWorks does, so the title block is there even without the .slddrt file), save templates in the org's SolidWorks version or older, title blocks that show the file and configuration names show the part number, revision and Name, and changing a template only changes new files.
- **User guide.** A new chapter, **How Litterbox works**: the vault as a Git repository and what each folder holds, Git LFS, locks and read-only files, how an upload syncs, checks and retries, batches, downloads on demand, and the **job queue** (one job at a time in order, busy parts, refreshes, errors that stay until dismissed). The Folders and Check In sections now cover what came late in 0.6.1: items straight in a top, Add Parts..., folders listed first, and the parts listed in the Check In window.
## 0.6.1

- **Report a problem.** Help > **Report a problem...** (and **Report...** in the red status bar's Details window) asks what you were doing, then makes a report and opens an email to the Litterbox team (contact+litterbug@halfcatrocketry.com) for you to send: with Outlook, a new message with the report attached; otherwise your email program, with Explorer showing the report to attach. The report has your comment, the versions of Litterbox, Windows, SolidWorks and Git, the problems in the status bar, the last unexpected errors with their details, Litterbox's log, your Litterbox settings and the vault's shared settings, with passwords and tokens taken out. Reports are kept in C:\Litterbox\logs\reports (the newest five).
- Errors in the window's own code (a button that fails) now show in the red status bar and go in a report, instead of being lost.
- **Configurations named after the part.** With SolidWorks open, Check In and Save Progress rename a model's configuration to the part's Name when it is the file's only configuration and is called "Default", so an assembly's tree shows `HCR-00042-001_A<1> (Bracket)` the way McMaster-Carr's parts show their catalogue number. When the Name changes, the configuration is renamed again at the next check-in. Import does the same to the files it copies in. Files with configurations of their own are left alone. Assemblies follow a renamed configuration (SolidWorks keeps an ID for each), and the configuration's BOM part number is set to the document's name, so a SolidWorks BOM still shows the part number. A file open in SolidWorks with unsaved changes isn't touched.
- **Configurations kept in the record.** Check In (with SolidWorks open) and Update BOM keep each revision's configurations, and which configuration of each part an assembly uses. A part's Details tab says when it has several ("they are all released together"). Check In warns, once it is done, when a configuration an assembly uses was deleted from a part (a renamed one is fine), when a part's configurations have different materials (Litterbox keeps the material of the one it was saved in), and when a part is linked to an outside design table or equations file. Update references says when the newer revision has lost a configuration the assembly uses.
- **Create Variant.** Create > **Create Variant...** copies the highlighted part to a new variant of its part number, as a part of its own at Rev A, with the original's Name (or another), checked out to you: for when a configuration really needs its own part number. Its SolidWorks files are copies of the latest revision's, the drawing pointed at the copied model.
- **Folders (Home).** A **Home / Vault** switch above the list: Vault is the parts list as before; Home is a tree of folders, each line a tick box, the number and the name. A folder points at parts, documents and ECOs, so the same part can be in any number of folders, and removing it from one (or deleting the folder) never touches the part. Three tops:
  - **Personal**: your own folders, kept on this computer only (C:\Litterbox\folders\<org>.yaml).
  - **Team**: the org's. Everyone sees them; Admins, the Owner and people with a role ticked **Team folders** (Team > Roles...) change them.
  - **Projects**: a folder for each project you are the Lead or a member of (Admins and the Owner see every project that isn't hidden). Its Lead changes it, and its members too unless the project window's **Only the Lead changes its folders** is ticked.
  - Right-click in Home: New Folder..., Rename..., Delete Folder..., Put the ticked here, Remove from This Folder, Details..., and the part actions. Drag items and folders onto folders (dragging into another top copies). Ticks in Home are the same ticks as in Vault, so Check Out, Release and the rest act on what is ticked there; clicking a part shows its details.
  - **Add to Folder...** in the Part menu, on the Documents screen and on the ECOs screen.
  - **Add Parts...** on a folder or a top (right-click): a search window of every part and document not in it yet; pick one or several (Ctrl or Shift) and Add.
  - Parts, documents and ECOs can go straight in a top (Personal, Team, a project), outside every folder: right-click it, drag onto it, or choose it in Add to Folder.... An older Litterbox doesn't show those.
  - In a top or a folder, the folders come first, then parts, documents and ECOs, each by number.
  - Two folder changes made very quickly could sometimes apply in the wrong order when the vault's folders folder held a file not named by time; fixed.
- **Check In and Save Progress list what they are about to check in** (number, revision and name) above the comment box. The comment can still be left blank.
  - Team and project folders are kept in the vault's new **folders** folder, one small file per change, so two people changing folders at once never clash, and a renamed project keeps its folders. An upload that changes folders the person may not change is refused (and the change taken back). An older Litterbox leaves the folder alone, so the vault doesn't need 0.6.1.
- `tools/run_tests.py` no longer crashes printing a failed test's output on a Windows console.

## 0.6.0

- **SolidWorks Toolbox parts.** Team > **Vault Settings...** has **SolidWorks Toolbox parts**, the team's Toolbox rule: **No Toolbox parts** (an assembly may use only parts in the vault: no Toolbox parts and no files from outside the vault), **Only the team's Toolbox** (Toolbox parts only from the team's own copy in the vault, and no other files from outside it), or **Don't check**. A new vault starts with No Toolbox parts; a vault made before 0.6.0 starts with Don't check. Setting a rule makes everyone in the vault need Litterbox 0.6.0.
  - **Check In** refuses an assembly that breaks the rule, names the files, and leaves it checked out. **Release** refuses it too, since a rule can be set after an assembly was checked in, and asks for **Update BOM** first for an assembly checked in without SolidWorks open (nothing read it).
  - What an assembly uses that isn't a Litterbox part is read with its parts at check-in and by Update BOM, and kept in its record for each revision, so Release needs no SolidWorks.
- **The team's Toolbox.** Team > **Toolbox...** shows the team's copy of the SolidWorks Toolbox, kept in the vault's new **toolbox** folder: how many files it has, how many are downloaded here, and whether this computer's SolidWorks uses it. Everyone can **Download** it. Only Admins and the Owner can change it: **Copy in a Toolbox folder...** (C:\SOLIDWORKS Data, say) makes it a copy of that folder and uploads it; **Let me change it** makes its files writable here, to add sizes in SolidWorks; **Upload changes** uploads them. Its files are read-only on everyone's computer, and Litterbox refuses to upload anyone else's change to it. An assembly can't be checked in with a Toolbox part made on this computer but not uploaded to the team's Toolbox yet.
  - SolidWorks takes every Toolbox part from the Toolbox folder it is set to use, whatever folder the assembly was saved with. So with Only the team's Toolbox, each computer's SolidWorks must be set to the team's folder (Tools > Options > System Options > Hole Wizard/Toolbox); after the first refresh Litterbox says so if it isn't, or if some of the team's Toolbox isn't downloaded yet.
- **File rules version 3.** Everything in the toolbox folder is stored with Git LFS and lockable (so read-only until locked). Admins are offered the update as before; it makes the vault need 0.6.0.
- **Ready for more CAD programs.** Everything SolidWorks-specific now sits behind one interface (`cad/cad_program.py`), reached through `cad/cad_programs.py` by each file's extension, so a second CAD program can be added without changing how anything works for SolidWorks users. Nothing in the window changes.
- **Windows that didn't fit.** Team > Toolbox... is wide enough for its buttons. Team > Vault Settings... is shorter and scrolls, with Cancel and Save always showing. Team > Doc Workflows... has shorter tabs (Release doc, Unrelease doc, Void doc, Remove doc link). Team > Roles... has a Superuser column wide enough for its heading at any display scaling.
- The user guide's **Decisions to make first** now points to the Toolbox rule and the team's Toolbox, and has a Toolbox parts section and a section on the team's Toolbox.

## 0.5.7

- **Upgrading records.** Litterbox can now bring a vault's part and document records up to a new record format when a later version needs one. Nothing changes yet: there is no new format, so the vault isn't touched. When there is one, an Admin or the Owner is asked once per session to upgrade (**Vault > Upgrade records...**, greyed out until then). The question says what changes and how many records. Upgrading makes everyone in the vault update Litterbox, then rewrites every record in one upload. A record someone has checked out is left for them, and is upgraded when they check it in. Until the vault is upgraded, the new version reads every record but changes none, so an older copy of Litterbox never meets a record it can't read.
- **User guide: Decisions to make first.** A new section in Getting started, for everyone: what is built into a team's CAD files and history once parts are released. Don't use Toolbox fasteners (or, if you must, share one copy as a document); one part per file, with no configurations; linked design tables as documents; at least 6 digits in the base number; one vault for the whole team; and which Git host to choose.

## 0.5.6

Nothing in the window changes: this release is faster and fixes a few things.

- **Faster.** The parts list refreshes sooner: it reads each part's record about six times faster, asks the vault's server for the lock list once instead of twice, and looks at the vault's folders faster on Windows. Every upload (Check In, Release, a sign-off, a settings change) asks the server one thing less, and Check In, Undo and the other actions that give locks back ask for the lock list once instead of twice. Checking in, undoing or releasing many parts at once asks git once for the whole batch where it asked once per part.
- **Files with letters like é or spaces in their names** are now seen as changed when they are. Litterbox asked git which files had changed in a form where git writes such names with escape codes, so they never matched.
- **Importing** no longer reads every file just to look for copies of files already in the vault: only files the same size and type as another are read. A source file whose path is longer than Windows usually allows no longer fails there.
- When something goes wrong part way through changing the vault's settings, team, workflows or document types, a settings file that git doesn't track is always put back as it was (one of these deleted it).
- The release pipeline runs the tests once for a tag, not twice, and the Windows tests now stop a release if they fail.

## 0.5.5

- **Rev comes second in the parts list**, right after the part number.
- **Form, Fit, Function and Dispo only with an ECO.** The Workflow and Review windows ask for and show them only when the request has an ECO. A workflow that doesn't require one (or a first release, which never has one) shows just Part, Name and Rev. A Release or Void without a workflow no longer asks them at all: the small "what changed" window is gone.
- **The Form, Fit and Function columns are always wide enough for their headings**, at any display scaling (they were cut off at higher scaling). Every column of that table now fits its heading and what it shows.
- **An ECO needs a description**, as well as a title: what changes, and why.
- **Project Leads, members, Restrict and Hide.** Team > **Projects...** now opens for everyone on the team and lists the projects you may see, each with its Lead, how many members it has, and whether it is restricted or hidden. Admins and the Owner add projects (**New Project...**), change them and delete them. **Edit** opens a **Project** window with the name, the digits, a **Project Lead**, the **members** (search the team, then **Add** and **Remove**), and two tick boxes, all optional:
  - **Restrict Project:** only its members, its Lead, Admins and the Owner may make part numbers in it, change its parts (check out, check in, release, revise, void and the rest), and ask for or sign its workflows. The Workflow window, Review's Reassign and All Workflows' Change signer only offer people who may sign; superusers may still sign. Its name only appears in New Part, New Assembly and Import for those who may use it.
  - **Hide Project:** restricted too, and nobody else sees it at all: Litterbox leaves its parts (records, CAD files, cancelled revisions) out of their copy of the vault, so their CAD files are never downloaded, and its ECOs out of their ECOs list. Someone added to it gets its parts at their next Get Latest; someone taken off loses them then.
  - Either one needs a Lead. A project's Lead may change everything about it but its digits, including its members; only Admins and the Owner may change its digits or delete it.
  - This is process control, like the rest of Litterbox's permissions: anyone with access to the vault on the Git host can still read all of it, and a hidden project's name and its part numbers in commit messages are not hidden.
- Changing a project makes the vault need Litterbox 0.5.5, so older copies, which would ignore the restrictions, can't work in it.

## 0.5.4

- **Form, Fit, Function and Dispo.** Releasing a part at Rev B or later now asks, for each part, what changed (**Form**, **Fit** and/or **Function** tick boxes) and what to do with the parts already made to the revision before (**Dispo**: Use As Is, Rework, Scrap or Return To Supplier). They are columns of the Workflow window's parts list; a part released at Rev A shows dashes there, since nothing earlier exists. Dispo starts blank and the workflow can't be submitted until every part that needs one has it. Without a workflow, Release asks the same in a small window first. What changed goes in the new revision's history, and the Dispo in the earlier revision's: pick the earlier revision on the Details tab and it says, for example, "Disposition: Scrap (Rev B released)". A void asks for a Dispo too, for the voided revision's parts. The ECO window lists both for each of its parts.
- **No ECO for a first release.** A release workflow whose parts are all at Rev A no longer asks for an ECO, even when its workflow requires one: a first release changes nothing. If any part is at Rev B or later, the ECO form appears. Other workflows ask for theirs as before.
- **The Workflow window**: the parts list is Part, Name, Rev ("A → B"), Form, Fit, Function, Dispo, with the Part column as wide as the org's part numbers. With an ECO, the sign-off list takes only the room it needs and the ECO's boxes take the rest. The ECO's **Name** is now called its **Title** everywhere.
- **Review in My Tasks.** Approve, Reject and Change signer are replaced by one **Review** button (or double-click a request). It opens the request as it was asked, read-only: its parts with what changed and the Dispo, the workflow, who signs and who has signed, and the ECO. **Open Drawing**, **Open PDF**, **Previous Drawing** and **Previous PDF** open the selected part's files at the new revision and the one before. Each sign-off of yours has a **Reassign** button, to hand it to someone else with the role (Undo takes it back). At the bottom: **Approve** (hands over the ones you reassigned, then approves the rest, with the optional comment), **Reject** (needs the comment), and **Reassign** (only once you have handed over every one of yours). The people you hand them to see the request in their My Tasks. All Workflows keeps its buttons, Change signer included.
- **Rejected requests come back to whoever asked.** Rejecting no longer ends a request. It leaves every signer's My Tasks and shows in the requester's as "rejected by ...: needs changes", with the comment. **Review** opens it in the Workflow window, filled in as it was asked: change the parts, people, Form/Fit/Function, Dispo or ECO and **Resubmit** (everyone signs again, and the same ECO carries on), or **Withdraw** it. Meanwhile its parts can be checked out and in as usual, but can't go into another workflow. The ECO stays open, with the rejection and the resubmission in its history.
- **Make COTS happens at the last sign-off**, like the other workflows; it no longer waits for the button to be pressed again.
- **Sharper menus.** Greyed-out menu entries no longer look blurred (Windows drew them with a white shadow, which smudged on the dark menus).
- Litterbox versions before 0.5.4 keep a rejected request's draft and the new history entries, but don't know a draft holds its parts: everyone in a vault should update.

## 0.5.3

- **The team's currency.** Team > **Vault Settings...** has **The team's currency** (US Dollar, Euro, Pound Sterling and 21 more, or none). Costs are then shown with its symbol: the unit cost on the Details tab, the BOM tab's Unit cost and Total cost columns and its total ($12.50; 12.50 kr for currencies written after the amount), and the symbol sits beside the Unit cost box in **Purchasing Info**. Typing the symbol yourself still works. The exported BOM `.csv` names the currency in its headings ("Unit cost (USD)") and keeps the cells as plain numbers, so a spreadsheet can add them up. Changing the currency doesn't convert any costs. Litterbox versions before 0.5.3 keep the setting without using it.
- **Materials.** Each part revision's **material** is kept in its record, as SolidWorks has it assigned (its active configuration; parts made in much older SolidWorks versions that only have an old-style material are read too). It is read when a part's model is checked in with SolidWorks open, and shows on the Details tab and in a **Material** column (View > Columns, off to start with). A part with no material in SolidWorks shows blank. A part checked in without SolidWorks open, or from before 0.5.3, shows **Not read yet**: **Part > Update Material** reads the ticked parts' materials, using SolidWorks if it's open or starting it out of sight and closing it afterwards. A part someone else has checked out is skipped; one you have checked out gets it in your copy, and it goes up with your next Check In. Litterbox versions before 0.5.3 keep the materials without showing them.
- **Material in the BOM.** The BOM tab and the exported `.csv` have a **Material** column: the material of the revision each line uses.
- **Saved BOMs are named `HCR-00042-001_A_BOM.csv`** (was `HCR-00042-001_A.CSV` in 0.5.2), so the name can't clash with another `.csv` a revision might have, such as a table a parametric part reads.
## 0.5.2

- **Part Workflows and Doc Workflows.** Team's Workflows... is now two buttons. **Part Workflows...** has the parts' Release, Unrelease, Void and Make COTS workflows; **Doc Workflows...**, under it, has Release document, Unrelease document, Void document and Remove document link. Each window's **Add standard workflows** adds only its own. The workflows themselves are unchanged.
- **Costs in the BOM.** The BOM tab and the exported `.csv` have a **Total cost** column: a line's unit cost times how many the whole assembly needs. The line above the BOM tab gives the assembly's **total cost**, from every part in it once, whichever list is shown, and says how many parts have no unit cost or aren't counted. The `.csv` ends with a "Total cost of the assembly" row. Costs are in the team's own currency, as unit costs are.
- **The BOM is saved at release.** When an assembly is released, Litterbox saves its indented BOM (quantities, purchasing info and costs as they are at that moment) beside the model as `HCR-00042-001_A.CSV`, uploaded in a commit of its own straight after the release, and its history records it. The revision keeps it: Revise doesn't copy it to the next revision. It needs no SolidWorks, so it is always made. Non-CAD kits don't get one. Assemblies released before 0.5.2 don't have one.
- **Vault > Vault Size...** shows how much the vault takes up on the host: its history (every commit) and every version of every file in Git LFS, each counted once, and how much of that is downloaded on this computer. It gets the latest list from the host first.
- **Documents are called documents.** Check Out, Check In, Release, Unrelease, Void and the rest say "Checked out 2 documents", "Release these 2 documents?" and so on when they act on documents, not "parts".
- The sidebar's **ECO** is **ECOs** again.
- **Parts you already have open in SolidWorks become writable when you check them out.** Until now a part open in SolidWorks stayed read-only after Check Out until you reloaded it with Read-only unticked. Now Litterbox does that for you: right after the check-out it asks the SolidWorks that is running (it never starts one) which of the parts' files it has open read-only and switches them to writable, keeping anything you've typed into them. A file the check-out replaced with a newer version is reloaded instead; if you had unsaved changes in it, Litterbox asks first. If SolidWorks says no (busy, a dialog open), the status line tells you to reload it yourself, as before.
- Fixed: Litterbox couldn't list what SolidWorks has open ("Member not found"), so the SolidWorks watcher (`solidworks_watch: true`) never saw any documents.
## 0.5.1

- **Non-CAD parts.** New Part and New Assembly have a **Kind**: CAD (the default) or **Non-CAD**, for things with no model: paint, glue, raw stock, wire, or a kit. A non-CAD part has a part number like any other and is checked out, checked in, released, revised, unreleased and voided the same way, without files (Open, Open Drawing, Generate STEP/PDF and Make COTS are greyed out for it). The parts list has a **Kind** column. **Edit Details** can switch a part between CAD and non-CAD until it is first released, as long as it has no SolidWorks files. The first non-CAD part makes the vault need Litterbox 0.5.1 or newer, since older versions would take it for a CAD part with no files yet.
- **BOM lines added by hand.** On the BOM tab of an assembly you have checked out, **Add item...** lists a part in its BOM with a quantity, and **Remove** takes such a line off. A CAD assembly takes only non-CAD parts this way (its CAD parts come from the model). A **non-CAD assembly** (a kit, made with New Assembly as Non-CAD) is built only this way, from any parts, CAD or not. The lines show in the BOM tab (marked "added by hand"), the exported `.csv`, Where used and the release checks, freeze at release and carry on to the next revision. They go up with your next Save Progress or Check In.
- **Documents.** A new **Documents** screen in the sidebar (below Workflows and ECO, Ctrl+5) keeps the org's documents: test procedures, plans, datasheets, review slides, anything. Documents don't use part numbers. An Admin or the Owner sets up **document types** in Team > **Document Types...**, each with a name and a prefix (Propulsion Document, PROP), and **New Document** numbers each one with the next free number for its type: PROP-0001, PROP-0002, ... (four digits, growing past them). A type documents use can be hidden but not removed.

- **Part numbers now loop.** Numbers count up from the vault's start number to the highest the digits allow (999999 for 6 digits), then start again at 1 and go up to just below the start number, so the start number is only the first point of a complete loop and every number gets used. Zero is never used. Voided parts keep their numbers.
- When every part number is taken, New Part, the suggested number and Import say so plainly ("this vault has no part numbers left") instead of complaining about the number of digits.
- **Import numbering counts from the lowest free part number.** It still proposes numbers about 100 ahead (plus a random extra, so two big imports started together are unlikely to collide), but the 100 is now counted from the lowest free part number, not from the highest one in use, so one number typed in far above the rest no longer pushes imports up with it. Past the highest number the digits allow, it loops round to 1. If someone takes a proposed number while you work, the numbers Litterbox chose are swapped for the next free ones when you finish, as before.
- Create new vault no longer warns about a high start number leaving little room, since the numbers loop round.

## 0.3.1

- **Actions on many parts are much faster.** Check Out, Check In, Save Progress, Undo Checkout, Release, Unrelease, Void and Make COTS, and every step of a workflow (asking, signing, finishing, withdrawing), now download once and upload once for the whole selection instead of once per part, and take and release locks several at a time. Each part still gets its own history entry. Changes to part records (workflow steps, Release, Unrelease, Void, Make COTS) go in one commit per batch, with a line for each part in its message; Check In and Save Progress still make one commit per part. If one part can't be done (somebody has it checked out, say) it is reported and the rest carry on; if the upload itself fails, nothing is left half done. Updating references on several assemblies, and Update references, work the same way.
- Parts you void are unselected automatically (they are hidden by default, so a leftover tick was invisible).
- Release, Unrelease, Void and Make COTS now work on several selected parts at once even in a vault with no workflow; before, they needed one part at a time.
- **Reopen is now called Unrelease** everywhere it is shown (the button, pop-ups, Team > Workflows and a part's history). Records and settings keep their old internal name, so nothing in an existing vault changes.
- **Buttons grey out** when they can't be used on what is selected: a button lights up only if every selected part suits it (for example Check Out is grey if any selected part is already checked out).
- Parts list: new **Deselect All** button.
- Import: "Import all as the same base number" box. Leave the number empty for the next free one, or type your own; if it is already in use the new variants start at the lowest free number. Litterbox refuses, and says so, if the parts won't fit in the variant numbers that are left.
- Import review: **Select All** and **Deselect All** buttons.
- Shift-click selects everything between the last click and this one in every list with boxes (Import, References).
- New vault setting commit_style: Check In and Save Progress on several parts make one commit per part (the default) or, if an Admin chooses it, one commit for the whole batch, which is faster (each commit takes about a second). Admins and the Owner change it in Team > Vault Settings...; it applies to everyone. The same dialog also edits release_rule (warn / block / off) and require_signatures, which were hand-edited in .litterbox/config.yaml before (turning signatures on asks first).
- Debug mode now logs where a batch's time went, e.g. `Timing: check in on 20 part(s) took 31.2s. git commit x20 = 19.8s; git push x1 = 6.1s; ...`.
- Very large batches (over 100 parts) now still make a single commit when one is asked for.

## 0.3.0

- Workflows are rebuilt. Pressing Release (or Reopen, Void, Make COTS) in a vault that has workflows for that action opens a Workflow window: pick a template (T1, T2... or your own), choose a person for each sign-off, add optional extra sign-offs, and submit. Several parts can go through one workflow together; the people sign once for the whole batch.
