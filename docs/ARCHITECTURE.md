# How the Litterbox code is laid out

For anyone changing the code: where things live, the rules the layout keeps, how to test, and how to add something
new. The automatic checks in `app/tests/architecture/` enforce the rules, so a change that breaks one fails the tests.

## The top of the repository

| Path | What it is |
|---|---|
| `app/main.py` | Starts the program (`python app/main.py`), and is what PyInstaller builds into `Litterbox.exe` |
| `app/litterbox/` | The program: one Python package, laid out below |
| `app/litterbox/gui/assets/` | The icons |
| `app/tests/` | The tests, in folders that mirror the package; shared helpers in `tests/support/` |
| `tools/solidworks/` | SolidWorks experiments (`sw_probe.py`, `sw_rename_test.py`) and their tests; not part of the program |
| `tools/package_map.py` | Prints the map in this file |
| `tools/run_tests.py` | Runs the tests in parallel (see Testing) |
| `tools/user_guide/` | Builds the user guide, `docs/Litterbox_User_Guide.docx` (needs python-docx) |
| `packaging/` | PyInstaller recipe, installer script, release scripts |
| `.github/workflows/` | `tests.yml` runs every test on every push; `release.yml` builds and publishes a tagged release |

## Layers

The package is built in layers. A module may import from its own layer and the layers below it, never from a layer
above (imports inside functions count too).

```
6  gui                 the window (gui/logic: its decisions, with no window code)
5  jobs  user  cli     the background queue; personal settings, updates, the build self-test; the command line
4  parts  team  workflows  references  importing  exporting  documents  change_orders  folders  vault  cad   the features
3  git                 the only place that runs git and git-lfs
2  records             the part records in PN-logs/*.yaml
1  core                part numbers, revisions, numbering order: pure rules
0  errors  diagnostics  layout  version  build_info  util          used by everything
```

The few imports that go up a layer are listed, each with its reason, in `KNOWN_EXCEPTIONS` in
`tests/architecture/test_layers.py`. That list may only shrink: a test fails when an entry is no longer needed.

## The rules

1. **One job per file.** A file's docstring says what it is for. Files stay under 450 lines (tests included).
2. **Layers** as above.
3. **Who may do what.** Only `git/` runs git (through `git/runner.run`). Only `cad/solidworks/` talks to SolidWorks
   (`win32com`, `pythoncom`), and nothing outside `cad/` imports it: the rest of Litterbox reaches a CAD program
   through `cad/cad_programs.py` (see "CAD programs" below). Only `gui/` imports `tkinter`/`customtkinter`, and never
   `gui/logic/`. The few modules that start other programs are listed, with what they run, in
   `tests/architecture/test_boundaries.py`.
4. **Call functions through their module:** `runner.run(...)`, not `from litterbox.git.runner import run`. A test can
   then replace `runner.run` and every caller sees it. Classes, constants and exceptions may be imported by name.
5. **No re-exports.** A package's `__init__.py` holds only a docstring; import each name from the file it lives in.
6. **Shared means public.** A name used by another file has no leading underscore. `_name` means "this file only".
7. **Module names never double as local names.** A module imported as `runner` must not also be a variable or
   parameter called `runner` in the same file: inside that function `runner.run` would be the variable's. That is why
   some modules have longer names (`lfs_locks`, `batch_core`, `record_store`, `team_identity`, `action_rules`, ...).
8. **Nothing on disk changes by accident.** The vault layout is in `layout.py`; changing it changes the vault format
   (`version.VAULT_FORMAT`), which needs a migration plan.

## Testing

| What | How |
|---|---|
| All tests, on Windows | from `app/`: `python -m unittest discover -s tests -t .` (the git tests are skipped on Windows) |
| All tests, in parallel | `python tools/run_tests.py` from the repository root: each test class in a process of its own, half the cores at once, slowest first (by the last run's times, in `tools/.test_times.json`); `tests.parts` (and so on) to run only some; `--jobs` to choose how many at once; `--split-over SECONDS` runs a slow class a test per process |
| All tests, everything | `python tools/run_tests.py --git` (the git tests too, on Windows); one at a time, the same as the first row with `LITTERBOX_GIT_TESTS=1` set, takes about 40 minutes |
| On GitHub | `tests.yml` runs everything on Linux on every push to a branch; `release.yml` calls it before building |
| The build | `python app/main.py --self-test` (the release pipeline runs it on the built program) |

- **Git tests** use a real bare "remote" with two clones (Alex and Bea, `tests/support/vault_fixture.py`) and a fake
  git-lfs that models locks (`tests/support/fake_git_lfs.py`).
- **Window tests** replace tkinter and customtkinter with stand-ins (`tests/support/gui_fakes.py`):
  `load_gui_with_fakes()` returns every window module, so a test reads `self.gui.app.App` and replaces
  `self.gui.request_dialog.WorkflowRequestDialog`. They check the wiring, not the look.
- **Architecture tests** (`tests/architecture/`) read the code and check the rules above, and that every module is
  in the map below.
- Never give a test file the name of a program module at the top of `tests/` (they are packages now, so the folders
  keep names apart, but `tests/config.py` once hid the real `config` module).

## Adding something

1. Pick the layer, then the folder (a new feature area gets its own folder at layer 4, and its window parts go under
   `gui/`: decisions in `gui/logic/`, dialogs in `gui/dialogs/`, bigger windows in `gui/windows/`, and a list that
   belongs in the main window as a screen of its own in `gui/screens/`, with an entry in the sidebar).
2. Give the module a name nothing in its callers uses as a variable, and a docstring that says what it is for.
3. Put its tests in the matching folder under `tests/`.
4. Run the tests: the architecture tests say if a rule is broken, and the self-test and the PyInstaller recipe find
   new modules on their own.
5. Run `python tools/update_architecture_map.py` to bring the map below up to date.

### CAD programs

Each CAD program Litterbox knows is a `CadProgram` (`cad/cad_program.py`, which lists what a program and its backend
provide), with its code under `cad/<program>/`: today only SolidWorks (`cad/solidworks/sw_program.SOLIDWORKS`). The
rest of Litterbox never imports a program's code. It asks `cad/cad_programs.py` for the program of a file (by its
extension), wraps its work in `cad_programs.session()` (SolidWorks needs COM switched on in the thread), and uses
`cad_programs.Backends()`, which behaves like one backend and hands each call to the backend of the program whose file
it is about. Which extensions are a program's parts, assemblies and drawings is in `core/file_types.py`, low enough for
the records to use. A second program: its extensions in `core/file_types.PROGRAMS`, a `CadProgram` under
`cad/<program>/` filling in what it can (the base class can do nothing, so a program without references or exports
still has its files versioned, locked and released), and that program in `cad_programs.PROGRAMS`. A program whose
designs are many files per revision (KiCad) would need a folder per revision, which is a new part of the vault layout.

The Toolbox rule (`core/toolbox_rules.py`, the vault setting `toolbox`) is checked at Check In and Release by
`parts/toolbox_check.py`, against what an assembly uses that isn't a Litterbox part: read with its references
(`reference_reader.read_other_files`, using the backend's `library_components`) and kept per revision in the record
(`records/record_other_files.py`). The team's own Toolbox is the vault's `toolbox/` folder (`vault/toolbox_admin.py`):
lockable and read-only (file rules version 3, `git/read_only.py`), and `team/guarded_push.toolbox_allowed` refuses an
upload that changes it unless the person is an Admin or the Owner.

Configurations (0.6.1): a backend reads a model's configurations (`configurations`, with SolidWorks' ID for each) and
which configuration each assembly component uses (`component_configurations`), and renames one
(`name_configuration`); SolidWorks' side is `cad/solidworks/sw_configurations.py`. Check-in reads them with the rest
(`reference_reader.read_configurations`) into the record's `configurations` (`records/record_configurations.py`),
first renaming a lone "Default" after the part (`core/configuration_names.py` decides, `parts/configuration_naming.py`
does it), and warns afterwards (`parts/configuration_check.py`). A backend handed to the reader or the namer is used in
its caller's `cad_programs.session()`: one that first connects inside a session of their own breaks when it ends.

Templates (0.6.2): the org's and each project's SolidWorks templates are the vault's `templates/` folder (the org's
at its top, a project's in `templates/<project>/`, `template_rules.folder_name`; a template is known by that path,
`Template.key`), with `templates/templates.yaml` saying each one's kind, owner and whether it is the default
(`vault/template_store.py`). A renamed project's folder is moved with `git mv` (`template_admin.rename_project`).
The rules (one default per kind and owner, a project's before the org's) are `core/template_rules.py`, with each
program's template extensions in `core/file_types.TEMPLATES`. `vault/template_admin.py` makes each change as one
uploaded commit, `vault/template_access.py` says who may, and `team/guarded_push.templates_allowed` compares the index
before and after an upload to refuse anyone else's. A backend's `new_from_template(template, out)` makes a part,
assembly or drawing (an empty sheet) from one, routed by `cad_programs.for_template`; `parts/from_template.py` makes a
part's model or drawing under its file name, for New Part / New Assembly (`create_actions.py`) and Create > New
Model... / New Drawing....

### Folders

Home's folders are a feature area of their own, `folders/` (layer 4): `folder_model.py` (a tree, built by applying
changes in order), `folder_store.py` (Team and project folders: one never-edited file per change in the vault's
`folders/` folder, `layout.FOLDERS_DIR_NAME`), `personal_folders.py` (a file per org on this computer),
`folder_access.py` (who sees and changes which; `team/guarded_push.folders_allowed` refuses an upload that breaks it)
and `folder_actions.py` (the checked changes the window asks for). The window side is `gui/main_window/home_view.py`
and `home_actions.py`, with the words in `gui/logic/folder_text.py`. Home shares the parts list's ticks, and
`PartsList._highlighted_pns` / `_ticked_pns` answer for whichever of the two is shown, so every action works from
either.

Problem reports: `user/bug_report.py` makes the zip, `user/report_mail.py` hands it to Outlook (through PowerShell) or
the default email program, and `gui/main_window/problem_reports.py` asks for the comment. Unexpected errors are kept
with their tracebacks by `diagnostics.note_unexpected` (the job queue and the window's `report_callback_exception`).

### Elsewhere

Download on demand lives in `git/lfs_download.py` (pointers, `git lfs pull`) and `parts/downloads.py` (what a part
needs). The SolidWorks watcher is `cad/solidworks/sw_watcher.py` (a thread of its own, not a job: it
polls), used by `gui/main_window/solidworks_watch.py`. The BOM is worked out in `references/bom.py` (from the records' `references` and
`quantities`, never saved; the parts are counted at check-in by `references/reference_reader.py`); copies out of the vault (Export Files, the BOM as a .csv) are in `exporting/`, whose `export_folder.py`
keeps every export outside `C:\Litterbox` and any repository. A part's purchasing fields are
`records/purchasing_info.py`, changed through `parts/purchasing.py`. The roadmap (`docs/REMINDERS.md`) has places
waiting: tickets and quality records as new folders at layer 4. Documents (`documents/`) are numbered like PROP-0001
(`core/doc_number.py`, a `DocNumber`) and kept like parts (records in `DOC-logs/`, files in `documents/`), so the
parts' actions work on them: `batch_core.as_pn`, `record_store` and `record_files` accept either number, and the
Documents screen points the main window's actions at documents with `App.act_on`.

## The command line

From `app/`: `python -m litterbox <command>`, with `status` (and the part actions), `new-part`, `scan`, `import` and
`init-vault`. `python -m litterbox <command> --help` lists each one's options. The commands are in `litterbox/cli/`.
